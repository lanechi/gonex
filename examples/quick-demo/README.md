# quick-demo

`quick-demo` 是 gonex 的完整运行与持续生成示例。它展示配置、PostgreSQL/GORM、
API/Controller/Logic/Service 分层、多 Server、生命周期，以及已有项目反复执行 `gx` 的兼容性。
`gx init` 的唯一项目模板是 [`../demo`](../demo/README.md)；本目录不作为初始化文件来源。

本目录是独立 module `github.com/lanechi/gonex/examples/quick-demo`，通过 `go.mod` 中的
`replace github.com/lanechi/gonex => ../..` 使用本地框架。

## 目录职责

```text
quick-demo/
├── api/                         # g.Meta 请求与响应定义
├── config/config.yaml           # Web Server 与 Logger 配置
├── internal/
│   ├── cmd/                     # Cobra 启动命令
│   ├── controller/              # gx 契约与开发者实现
│   ├── database/                # GORM 初始化与关闭
│   ├── logic/                   # 业务实现与注册聚合
│   ├── model/                   # 业务模型和生成 Entity
│   └── service/                 # gx 生成的 Service 接口
├── .env.example
├── go.mod
└── main.go
```

## 运行命令

直接执行不启动服务，只显示 Cobra 帮助：

```bash
go run .
```

默认业务 Server，监听 `:8000`：

```bash
go run . serve
```

命名 admin Server，监听 `:8001`：

```bash
go run . admin
go run . serve-admin
go run . serve2
```

使用 `WithName` 和 `WithAddress` 的 user Server，监听 `:8002`：

```bash
go run . user
go run . admin-with-address
go run . serve3
```

## 路由

默认 `serve` 注册用户资源：

```text
POST   /user
GET    /user
GET    /user/:id
PUT    /user/:id
DELETE /user/:id
```

Hello API 在不同命令中使用不同 Group 前缀：

- `serve`：`/hello`；
- `admin`：`/admin`；
- `user`：`/user`。

同一路径下的具体动作以 `api/hello/v1` 中的 `g.Meta` 为准；`api/<module>/<module>.go` 保留模块级
API 包，版本目录保留具体请求/响应。每个 Server 都提供自己的
`/openapi.json` 与 `/docs/`。

### 可测试的订单链路

默认 `serve` 的 `POST /hello/order` 是完整的 API → Controller → `service.Testservice()` →
Logic 示例。它通过 JSON 绑定订单内容、通过 query 绑定来源，并在进入 Controller 前执行校验：

```bash
curl -i -X POST 'http://localhost:8000/hello/order?source=web' \
  -H 'Content-Type: application/json' \
  -d '{"customerName":"Lane","quantity":2}'
```

成功响应中的 `data.id` 为 Logic 产生的可观察业务结果（`1000 + quantity`），`data.customerName`
为 Logic 返回的 `accepted:<name>`。缺少 `source`、名称少于三个字符，或 `quantity` 不在 1–100
之间时框架会返回 `400`，不会调用 Controller/Logic。`GET /hello/order/:id` 也演示 path 绑定；
`id` 必须大于零，例如：

```bash
curl -i 'http://localhost:8000/hello/order/42'
```

## 数据库配置

运行时和 `gx dao` 都从项目根目录 `.env` 或系统环境变量读取 `DATABASE_*`，系统环境变量优先；
数据库连接不放进 `config/config.yaml`。

最小 PostgreSQL 配置：

```dotenv
DATABASE_DRIVER=postgres
DATABASE_DSN=host=127.0.0.1 user=postgres password=password dbname=app port=5432 sslmode=disable TimeZone=UTC
DATABASE_LOG_LEVEL=warn
DATABASE_LOG_SLOW_THRESHOLD=200ms
```

`.env.example` 列出 PostgreSQL 的 DSN、URL 与分字段配置。GORM 日志通过
`github.com/lanechi/gonex/contrib/gormlog` 接入框架 Logger。数据库由应用初始化，并在
`server.OnStop` 中关闭。

## 使用本地 gx 重新生成

先从 gonex 仓库根目录构建：

```bash
cd gx
go build -o /tmp/gx .
cd ../examples/quick-demo
```

先预览，再生成现有契约：

```bash
/tmp/gx ctrl --dry-run
/tmp/gx service --dry-run
/tmp/gx ctrl
/tmp/gx service
```

生成新资源：

```bash
/tmp/gx ctrl order --dry-run
/tmp/gx service order --dry-run
/tmp/gx ctrl order
/tmp/gx service order

# 补充 API、Controller 和 Logic 后重新同步契约
/tmp/gx ctrl --dry-run
/tmp/gx service --module order --dry-run
/tmp/gx ctrl
/tmp/gx service --module order
```

准备数据库后生成模型：

```bash
/tmp/gx dao --tables users
```

## 文件所有权

- 带 `Code generated by Gonex CLI tool. DO NOT EDIT.` 的 Controller 模块契约、构造函数、Service 和模型文件由
  `gx` 管理；
- API 定义、Controller 动作实现和 `internal/logic/<module>` 首次生成后由开发者维护，不带
  `DO NOT EDIT`；
- `internal/logic/logic.go` 的 blank import 由 `gx service` 增量维护；
- `internal/dao` 与 `internal/model/entity` 是 `gx dao` 生成区域，不放手写业务代码；生成先在 staging
  中完成并校验，失败会回滚，成功仍会完整替换旧生成内容。

## 与 gx 的同步要求

生成命令、受管文件边界或现有项目兼容性变化时，必须同步本示例并重新执行 `ctrl --dry-run` 与
`service --dry-run`。项目初始化结构由 `examples/demo/` 与 `gx init` 下载/解包测试共同维护；
本示例负责证明升级后的框架和 gx 仍能作用于已有项目。

## 验证

```bash
go test ./...
go vet ./...
```

若修改了生成器，再使用本地 `/tmp/gx` 运行 `ctrl --dry-run` 与 `service --dry-run`，确认没有意外
