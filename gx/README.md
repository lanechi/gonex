# gx 代码生成器

`gx` 是 gonex 的独立开发期工具，module 为 `github.com/lanechi/gonex/gx`。它不参与 HTTP
请求运行时，负责创建项目以及生成 Controller、Service、GORM DAO 和 Entity。

## 安装与构建

远程安装：

```bash
go install github.com/lanechi/gonex/gx@latest
gx --help
```

`gx` 是仓库子目录中的独立 Go module。发布正式版本时，Git tag 必须使用
`gx/vX.Y.Z` 形式，例如 `gx/v0.2.0`；推送该 tag 后，`@latest` 才会稳定解析到对应版本。

在仓库内构建开发版本：

```bash
cd gx
go build -o /tmp/gx .
/tmp/gx --help
```

所有生成命令都从当前目录向上查找最近的 `go.mod`，因此可以从项目子目录执行；生成根目录仍以
发现的 module root 为准。

## 命令总览

| 命令 | 作用 |
| --- | --- |
| `gx completion` | 生成 Bash、Zsh、Fish 或 PowerShell 补全 |
| `gx init` | 下载规范 `examples/demo/` 并初始化 PostgreSQL 项目 |
| `gx ctrl` | 从 `api/` 请求定义生成 Controller |
| `gx service` | 从 `internal/logic/` 生成 Service 接口 |
| `gx dao` | 从数据库表生成 GORM DAO 与 Entity |

查看实时帮助：

```bash
gx --help
gx init --help
gx ctrl --help
gx service --help
gx dao --help
```

## gx init

```bash
gx init [path] --module example.com/my-project
```

常用参数：

| 参数 | 作用 |
| --- | --- |
| `--module string` | Go module 路径；省略时使用目标目录名 |
| `--name string` | 项目/命令名称；省略时使用目标目录名 |
| `--template-url string` | 覆盖模板 archive URL，供镜像和测试使用 |
| `--force` | 允许用完整模板替换非空目标目录 |
| `--dry-run` | 只输出下载和创建计划，不联网、不写文件 |

示例：

```bash
gx init ./my-project --module example.com/my-project
cd my-project
go mod tidy
go run . serve
```

主要输出：

```text
my-project/
├── AGENTS.md
├── README.md
├── .agents/skills/
├── .codex/agents/
├── api/hello/hello.go
├── api/hello/v1/hello.go
├── config/config.yaml
├── internal/
│   ├── cmd/
│   ├── controller/hello/
│   ├── database/
│   ├── logic/hello/
│   └── service/
├── resource/
├── .env.example
├── go.mod
└── main.go
```

`gx init` 不在二进制中维护项目字符串模板。正式版从同一仓库的 `gx/vX.Y.Z` tag 下载 `examples/demo/`，
pseudo-version 从对应 commit 下载，只有本地 `(devel)` 构建使用 `main`；`--template-url` 可指向同格式
的测试或镜像 archive。下载体、解压后总大小、
单文件和条目数均有限制；绝对路径、`..`、反斜杠、符号链接、硬链接和特殊文件会被拒绝。必要文件、
根 `.env` 的 `.gitignore` 规则、canonical module、项目名和 PostgreSQL driver 校验通过后，才在 staging 中替换 module/项目名并
提交目标。失败不会修改已有目标。

Controller、Service 等普通生成写入统一经过 `internal/gen/fs` 的 staging transaction，先校验项目相对路径，
再提交生成文件；DAO/Entity 继续使用双目录替换事务，以保证两个生成目录成对更新和失败回滚。

仓库内 `examples/demo/go.mod` 使用本地 `replace` 以便 CI 验证；初始化时该 `replace` 和占位 gonex requirement
会被移除。进入新项目运行 `go mod tidy` 后，Go 会解析当前发布的 gonex 版本。`--force` 会先备份再
整体替换目标，而不是合并文件；使用前应确认目录可以被替换。新项目已经提交后若旧备份清理失败，
命令会返回错误并明确保留的备份路径，不会静默报告成功。

## gx ctrl

从 `api/` 扫描请求/响应类型并生成 Controller 契约：

```bash
gx ctrl
gx ctrl user
gx ctrl user,order
gx ctrl user/v1/newapi
gx ctrl user --dir /user/v1
```

参数：

| 参数 | 作用 |
| --- | --- |
| `--dir string` | `api/` 下的相对扫描目录，例如 `/user/v1` |
| `--dry-run` | 只输出计划 |
| `--clean` | 删除已经失效且由 gx 拥有的 Controller 契约文件 |

生成目录为 `internal/controller/<module>/`。同时会在 `api/<module>/<module>.go` 维护模块级接口。Controller 目录通常包含：

- `<module>.go`：生成标记和包声明；
- `<module>_new.go`：各版本 `Controller` 类型与构造函数，可重生成；
- 动作实现文件：首次创建后由开发者维护，生成器不会覆盖非生成内容。

响应类型可以是 struct，也可以是命名 slice、map、标量或它们的指针；框架会交给统一 JSON 编码器处理。
生成器默认使用 `*Res` 契约，并在新建动作实现中使用 `new(Res)` 初始化，因此命名 slice、map 和标量响应也能
直接通过生成代码编译。

命名模式还会首次创建 `api/<module>/<module>.go` 和 `api/<module>/<version>/*.go`。API 与动作实现不带 `DO NOT EDIT`，创建后
由开发者补充真实参数和业务映射；模块级 API 接口由 `gx ctrl` 生成，后续使用扫描模式同步契约。

带 `Code generated by Gonex CLI tool. DO NOT EDIT.` 的文件属于生成器。`--clean` 前先运行
`--dry-run` 检查删除计划。

## gx service

从 `internal/logic/<module>` 的导出方法签名生成 Service：

```bash
gx service
gx service --module user
gx service user
gx service user,order
gx service --dry-run
```

名称参数和 `--module` 不能同时使用。生成结果写入 `internal/service/`，每次生成都会用最新 Logic
签名覆盖对应 Service 文件；生成器还会维护
`internal/logic/logic.go` 中的 blank import，以触发 Logic 注册。已不存在 Logic 模块的 gx 受管
import 会被删除，用户添加的其它 import 和代码保持不变。

所有业务实现保留在 Logic 包。Controller 依赖 Service 接口，不直接依赖具体 Logic 类型。
命名模式首次创建的 Logic 不带 `DO NOT EDIT`，由开发者替换占位模型并实现业务；后续使用
`gx service --module <module>` 从真实导出方法重生成 Service。

## gx dao

`gx dao` 从项目根目录 `.env` 和系统环境变量读取 `DATABASE_*`，系统环境变量优先。它不读取
Web 的 `config.yaml` 数据库配置。

```bash
gx dao
gx dao --tables users,orders
gx dao --tables public.users,billing.invoices
```

`gx dao` 是独立的数据库模型生成命令，支持 SQLite、MySQL/MariaDB/TiDB、PostgreSQL 和 SQL Server；
这不会向 `gx init` 项目加入相应运行时 driver。规范模板 `examples/demo` 的 `internal/database/database.go` 只使用
PostgreSQL。最小 PostgreSQL 配置：

```dotenv
DATABASE_DRIVER=postgres
DATABASE_DSN=postgres://postgres:password@127.0.0.1:5432/app?sslmode=disable
```

也可使用 `DATABASE_URL`，或组合 `DATABASE_HOST`、`DATABASE_PORT`、`DATABASE_USER`、
`DATABASE_PASSWORD`、`DATABASE_NAME`。PostgreSQL 支持 `schema.table`；多个 schema 会生成对应
子目录。

生成目录：

```text
internal/dao/**/*.gen.go
internal/model/entity/**/*.gen.go
```

`gx dao` 会先在 module 内的临时目录生成、修复数据库注释可能造成的非法 struct tag，并校验全部
Go 文件；验证通过后才成对替换 DAO/Entity。后续依赖更新或 `go mod tidy` 失败时，旧生成目录、
`go.mod` 和 `go.sum` 会回滚。成功执行仍是完整重建，会删除数据库中已不存在的生成项；禁止把业务
手写代码放进上述目录，执行前仍需确认 `.env` 指向正确数据库。生成成功但旧备份无法清理时，命令
返回错误并保留可定位的备份目录。

## 生成文件所有权

| 文件 | 所有者 |
| --- | --- |
| 带 `DO NOT EDIT` 的 Controller 契约、Service、聚合、DAO/Entity | gx 或底层 GORM Gen |
| Controller 动作实现 | 开发者；gx 只首次创建 |
| `internal/logic/<module>` | 开发者 |
| `internal/logic/logic.go` 的 blank import | gx 增量维护 |
| `api/` 请求与响应 | 开发者；命名资源生成时可创建标准初始文件 |
| `README.md`、`AGENTS.md` | `gx init` 创建，之后由项目维护 |

生成器必须满足：dry-run 不写文件、重复运行幂等、不覆盖非 gx 所有文件、错误中包含目标路径和
操作上下文。

## 推荐工作流

```bash
gx init ./my-project --module example.com/my-project
cd my-project
go mod tidy

gx ctrl user
gx service user

# 补充真实 API 参数、Controller 映射和 Logic 业务实现后：

gx ctrl --dry-run
gx service --module user --dry-run
gx ctrl
gx service --module user
go test ./...
```

数据库准备完成后再执行：

```bash
gx dao --tables users
go mod tidy
go test ./...
```

## 开发与同步

`gx` 的测试统一位于 [`test/`](test/)；`internal/` 目录只保留生产代码。

修改生成器时在本目录验证：

```bash
go test ./...
go vet ./...
```

数据库生成测试：

```bash
# CLI、ctrl/service/init 和生成器单元测试；SQLite 集成测试也会执行
go test ./...

# 只运行三种数据库的模型生成测试
go test -run 'TestDatabaseModelGeneration/(sqlite|postgres|mysql)' ./test

# PostgreSQL：优先使用这个 DSN，否则 GX_TEST_POSTGRES=1 时读取 gx/.env 的 DATABASE_* 配置
GX_TEST_POSTGRES=1 \
  go test -run 'TestDatabaseModelGeneration/postgres' ./test
GX_TEST_POSTGRES_DSN='postgres://user:password@127.0.0.1:5432/app?sslmode=disable' \
  go test -run 'TestDatabaseModelGeneration/postgres' ./test

# MySQL：密码只通过环境变量传入；未指定数据库时测试会临时创建并清理数据库
GX_TEST_MYSQL_USER=root GX_TEST_MYSQL_PASSWORD='your-password' \
  go test -run 'TestDatabaseModelGeneration/mysql' ./test
```

PostgreSQL 需要显式设置 `GX_TEST_POSTGRES=1` 或提供 `GX_TEST_POSTGRES_DSN`，避免普通 `go test ./...` 意外连接开发数据库；MySQL 需要提供 `GX_TEST_MYSQL_PASSWORD` 或完整 DSN。配置已提供但连接或建表失败时测试会失败，便于发现数据库问题。

生成契约变化还必须：

1. 更新 `internal/gen` 或 `internal/cli` 测试；
2. 同步并测试 [`examples/demo/`](../examples/demo/README.md)，它是 `gx init` 的唯一模板来源；
3. 使用 fake archive 测试下载、路径安全、清单验证、标识替换、dry-run 与失败原子性；
4. 使用 module 根目录入口 `go run .` 或本地构建的 `gx` 在临时项目验证生成结果；
5. 同步 `examples/quick-demo` 的对应生成文件和 README；
6. 更新本 README、根 README 和 [`examples/demo/.agents/skills/`](../examples/demo/.agents/skills/) 中受影响的生成工作流；
7. 架构边界变化时更新 `docs/architecture.md`。

完整规则见仓库根目录的 [`AGENTS.md`](../AGENTS.md)。
